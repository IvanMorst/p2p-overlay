## Проектное решение

Зафиксировано до реализации последующих этапов (веха E1-1).

| Параметр | Значение | Обоснование |
|---|---|---|
| Уровень | упрощённый | закрывает обязательный объём ТЗ; продвинутые пункты оформляются отдельными расширениями |
| Число узлов `N` | 13 | середина рекомендуемого диапазона 12–15; оставляет ресурс для отказов |
| `K_BUCKET_SIZE` | 3 | требование упрощённого уровня |
| `ALPHA` | 3 | фиксировано ТЗ для обоих уровней |
| `R` (репликация) | 3 | требование раздела 10.3 |
| Ретрансляторов в туннеле | 2 (конфигурируемо до 3) | минимум упрощённого уровня; 3 — расширение |
| Язык | Python 3.11+ | читаемость сетевой и криптографической логики, `asyncio` для параллельных RPC |
| Транспорт | TCP + собственное кадрирование | требование раздела 8 |
| Сериализация | CBOR, канонический режим | бинарность, поддержка `bytes`, детерминированность для подписей |
| Защита канала | TLS 1.3, взаимная аутентификация, привязка ключа к `NodeID` | раздел 11.2 |
| Криптография | `cryptography` (Ed25519, TLS) | запрет на собственную реализацию примитивов |
| Bootstrap-схемы | `star`, `ring` (расширение: `tree`, `multi-seed`) | раздел 14 |
| Развёртывание | независимые процессы; Docker Compose — расширение | раздел 14 |

`NodeID` вычисляется по формуле раздела 9 ТЗ. Разрядность `NODE_ID_BITS`
вынесена в конфигурацию (по умолчанию 256 бит — полная формула); меньшее
значение допустимо как исследовательский параметр раздела 14.

## Обзор

Узел — долгоживущий процесс на Python 3.11+, использующий `asyncio`. Внешние
связи — TCP, защищённый TLS 1.3. Поверх транспорта работают подсистемы:
идентичность, DHT, туннели, прикладные сервисы, метрики. Подсистемы
взаимодействуют через явные интерфейсы; прикладной слой не имеет доступа к
k-bucket и локальному хранилищу DHT.

Схема взаимодействия:

```text
        ┌────────────────────────────────────────────────────────┐
        │ CLI / локальный интерфейс управления / сценарии        │
        └───────────────┬────────────────────────────────────────┘
                        │ фасад Node
        ┌───────────────▼────────────────────────────────────────┐
        │ Node: join, lookup_node, put_record, get_record,       │
        │       build_tunnel, send_via_tunnel, state             │
        └───┬───────────┬────────────┬────────────┬──────────────┘
            │           │            │            │
     ┌──────▼────┐ ┌────▼─────┐ ┌────▼─────┐ ┌────▼──────────┐
     │ DHT       │ │ Security │ │ Tunnel   │ │ Metrics       │
     │ routing   │ │ TLS 1.3  │ │ manager  │ │ JSONL events  │
     │ rpc       │ │ trust    │ │ data     │ │ counters      │
     │ lookup    │ │ replay   │ │ e2e      │ │ snapshots     │
     │ records   │ └────┬─────┘ └────┬─────┘ └───────────────┘
     │ storage   │      │            │
     └────┬──────┘      │            │
          │        ┌────▼────────────▼─────┐
          └────────► Transport (TCP)       │
                   │ frame, codec, tcp     │
                   └───────────────────────┘
```

## Подсистемы

| Подсистема | Назначение | Модули | Статус |
|---|---|---|---|
| Transport | TCP, кадрирование, тайм-ауты, сериализация, корреляция RPC | `transport/frame.py`, `transport/tcp.py`, `transport/codec.py` | реализовано |
| Identity and Security | долговременная идентичность, `NodeID`, `HELLO`, TLS 1.3, проверка ключа, replay-защита | `identity.py`, `peers.py`, `security/` | этап 4 |
| DHT and Discovery | XOR-метрика, k-bucket с LRU, bootstrap, RPC, итеративный lookup, записи, TTL, репликация | `dht/` | этап 2 (поиск), этап 3 (записи) |
| Tunnel Management | построение, состояние, передача, контроль, перестроение | `tunnel/` | этап 5 |
| Application Services | текстовые сообщения, подтверждения, история | `app/` | этап 5 |
| Metrics and Experimentation | события, счётчики, экспорт JSONL/CSV | `metrics/events.py` | реализовано (базово) |
| User Interface | консольный интерфейс, локальный интерфейс управления | `cli.py`, `control.py` | реализовано (этап 2) |

## Границы модулей

- `transport.frame` — структуры кадра и словари типов, без I/O;
- `transport.codec` — канонический CBOR;
- `transport.tcp` — `StreamDecoder`, `Connection`, `serve`, `connect`; не
  знает о DHT, идентичности и туннелях;
- `identity` — ключи, `NodeID`, подписи;
- `peers` — рукопожатие `HELLO`, проверка идентичности, кэш соединений;
- `dht.routing` — k-bucket и таблица, без сети;
- `dht.rpc` — клиентская сторона RPC, использует `PeerManager`;
- `dht.service` — серверная сторона RPC, использует таблицу и хранилище;
- `dht.lookup` — итеративный поиск, использует `routing` и `rpc`;
- `dht.record`, `dht.storage` — подписанные записи и локальное хранилище;
- `node` — единственная точка сборки подсистем;
- `control` — локальный интерфейс, не часть оверлейного протокола.

Транспорт не знает о DHT: всё вышележащее использует `Connection.send()`,
`Connection.request()` и колбэк `on_frame`.

## Транспорт

TCP предоставляет поток байтов и не сохраняет границы прикладных сообщений,
поэтому реализовано собственное кадрирование. Заголовок — 24 байта:
`version(1) + type(1) + flags(2) + request_id(16) + payload_length(4)`.
`MAX_FRAME_PAYLOAD = 65 536`. Значение длины проверяется до выделения буфера.

`StreamDecoder` корректно обрабатывает частичный заголовок, частичный payload,
несколько кадров в одном чтении и разрыв внутри кадра. Один `read()` никогда не
считается одним кадром.

`Connection` сопоставляет ответ с запросом по `request_id` и проверяет
ожидаемый тип ответа: ответ с другим типом не принимается как ожидаемый.
Прикладной обработчик кадра вызывается после проверки корреляции; ответ без
ожидающего запроса отбрасывается.

## Идентичность

При первом запуске создаётся пара Ed25519 и сохраняется в
`state_dir/identity/`. `NodeID = SHA-256(DER SPKI открытого ключа)`, усечённый
до `NODE_ID_BITS`. При повторном запуске из того же каталога `NodeID`
сохраняется. Любой полученный открытый ключ повторно хешируется и сверяется с
заявленным `NodeID`.

Каждое соединение начинается обменом `HELLO`/`HELLO_OK`, поэтому прикладной
слой никогда не видит неаутентифицированного собеседника. Для защищённого
канала дополнительно сверяется ключ из TLS-сертификата.

## DHT

`RoutingTable` содержит `NODE_ID_BITS` k-bucket по `K_BUCKET_SIZE` контактов.
Индекс bucket — длина общего префикса, то есть `bit_length(XOR) - 1`.
Контакты упорядочены по времени последнего наблюдения (LRU). При заполненном
bucket новый контакт не вытесняет старый: наименее недавний контакт
проверяется `PING`, и только недоступный заменяется.

Итеративный поиск опрашивает до `ALPHA` кандидатов параллельно, расширяет пул
ответами и завершается, когда все `k` ближайших известных кандидатов
опрошены, либо когда не осталось неопрошенных кандидатов, либо по лимиту
итераций. Каждый поиск пишет в журнал `lookup_id`, инициатора, цель, шаги по
итерациям, число RPC, тайм-ауты и длительность.

## Публичный фасад узла

Прикладной слой обращается к узлу только так:

```text
join(bootstrap_peers)
lookup_node(target_node_id)
put_record(key, signed_record, ttl)
get_record(key)
build_tunnel(destination_node_id, constraints)
send_via_tunnel(tunnel_id, payload)
close_tunnel(tunnel_id)
get_network_state()
```

Прикладной слой не изменяет k-bucket и локальное хранилище напрямую.

## Локальный интерфейс управления

`control.py` поднимает сокет на петлевом интерфейсе (по умолчанию выключен,
`[control] port = 0`) и позволяет CLI и сценариям эксперимента читать состояние
и выполнять команды работающего узла. Это не часть оверлейного протокола:
формат — 4 байта длины + CBOR-словарь, TLS не используется, внешние адреса не
принимаются.

## Статус реализации

- Этап 1: каркас, транспорт, кадрирование, TCP-сервер и клиент — реализовано.
- Этап 2: идентичность, `NodeID`, `HELLO`, k-bucket, `PING`/`FIND_NODE`,
  итеративный lookup, bootstrap `star`/`ring`, CLI — реализовано.
- Этап 3: `STORE`/`FIND_VALUE`, подписи, TTL, репликация — в работе.
- Этап 4: защищённая TLS 1.3 сессия, negative-тесты — в работе.
- Этап 5: туннель и прикладные сообщения — в работе.
- Этап 6: масштабирование и сценарии отказов — план.
- Этап 7: эксперимент и графики — план.
