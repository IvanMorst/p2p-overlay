## Транспорт

Основной транспорт — TCP. TCP предоставляет поток байтов и не сохраняет
границы прикладных сообщений, поэтому используется собственное кадрирование.
UDP в текущей версии не используется.

## Формат кадра

Заголовок — ровно 24 байта, многобайтовые поля — в сетевом порядке байтов
(big-endian).

| Поле | Смещение | Размер | Тип | Назначение |
|---|---:|---:|---|---|
| `version` | 0 | 1 | uint8 | версия протокола, сейчас `1` |
| `type` | 1 | 1 | uint8 | тип сообщения |
| `flags` | 2 | 2 | uint16 | битовые признаки |
| `request_id` | 4 | 16 | bytes | сопоставление запроса и ответа, дедупликация |
| `payload_length` | 20 | 4 | uint32 | длина payload в байтах, big-endian |
| `payload` | 24 | перем. | bytes | сериализованные данные либо ciphertext |

Структура заголовка в коде: `struct.Struct(">BBH16sI")`.

`MAX_FRAME_PAYLOAD = 65 536`. Значение `payload_length` проверяется **до**
выделения буфера под payload: при превышении поднимается `PayloadTooLarge`,
соединение закрывается, узел продолжает работу.

`request_id` генерируется инициатором случайно (16 байт из `uuid4`) для каждого
запроса. Ответ обязан содержать тот же `request_id`; ответ с иным
идентификатором не сопоставляется с ожидающим запросом, и запрос завершается
по тайм-ауту.

## Флаги

| Флаг | Значение | Назначение |
|---|---:|---|
| `FLAG_RESPONSE` | `0x0001` | кадр является ответом |
| `FLAG_ERROR` | `0x0002` | кадр содержит ошибку |
| `FLAG_FRAGMENT` | `0x0004` | фрагментация (зарезервировано) |

Остальные биты зарезервированы: при чтении игнорируются, при записи — `0`.

## Типы сообщений

| Код | Имя | Направление | Назначение |
|---:|---|---|---|
| `0x00` | `HELLO` | запрос | представление узла на новом соединении |
| `0x01` | `PING` | запрос | проверка доступности |
| `0x02` | `PONG` | ответ | ответ на `PING` |
| `0x03` | `HELLO_OK` | ответ | подтверждение идентичности собеседника |
| `0x10` | `FIND_NODE_REQUEST` | запрос | поиск контактов, близких к цели |
| `0x11` | `FIND_NODE_RESPONSE` | ответ | список контактов |
| `0x20` | `STORE_REQUEST` | запрос | сохранение подписанной записи |
| `0x21` | `STORE_RESPONSE` | ответ | подтверждение или отказ хранителя |
| `0x30` | `FIND_VALUE_REQUEST` | запрос | поиск значения по ключу |
| `0x31` | `FIND_VALUE_RESPONSE` | ответ | значение либо близкие контакты |
| `0x40` | `TUNNEL_BUILD` | запрос | построение туннеля |
| `0x41` | `TUNNEL_BUILD_OK` | ответ | ретранслятор подтвердил включение |
| `0x42` | `TUNNEL_BUILD_FAIL` | ответ | ретранслятор отказал |
| `0x43` | `TUNNEL_DATA` | запрос | данные туннеля |
| `0x44` | `TUNNEL_ACK` | ответ | подтверждение передачи |
| `0x45` | `TUNNEL_CLOSE` | запрос | закрытие туннеля |
| `0x50` | `APP_MESSAGE` | запрос | прикладное сообщение |
| `0x51` | `APP_ACK` | ответ | подтверждение доставки |
| `0x7F` | `ERROR` | любой | ошибка протокола |

## Коды ошибок

Payload `ERROR` — CBOR-словарь `{"code": <int>, "detail": <str>}`.

| Код | Имя | Назначение |
|---:|---|---|
| `0x01` | `BAD_VERSION` | неподдерживаемая версия |
| `0x02` | `BAD_TYPE` | неизвестный тип сообщения |
| `0x03` | `PAYLOAD_TOO_LARGE` | превышение `MAX_FRAME_PAYLOAD` |
| `0x04` | `BAD_PAYLOAD` | payload не декодируется |
| `0x05` | `UNEXPECTED_REQUEST_ID` | неизвестный `request_id` |
| `0x06` | `TIMEOUT` | истёк тайм-аут |
| `0x07` | `INTERNAL` | внутренняя ошибка |
| `0x08` | `IDENTITY_MISMATCH` | `NodeID` не связан с ключом либо не совпал с ожидаемым |
| `0x09` | `BAD_RECORD` | запись DHT недействительна |
| `0x0A` | `REPLAY_DETECTED` | повтор кадра в текущей сессии |
| `0x0B` | `NOT_FOUND` | значение отсутствует |
| `0x0C` | `TUNNEL_FAILED` | туннель не построен или разорван |

## Сериализация payload

Основной формат — CBOR (`cbor2`) в каноническом режиме: ключи словаря
сортируются, числа кодируются минимальным представлением. Каноничность
обязательна для подписи записей DHT и для детерминированного вычисления
`NodeID`.

Сравнение форматов (измерение выполняется скриптом `tools/compare_codecs.py`,
сумма по пяти типовым структурам протокола):

| Формат | Размер | Бинарные данные | Каноничность | Валидация |
|---|---|---|---|---|
| JSON | 907 байт | требует base64 | порядок ключей зависит от порядка вставки | схема внешняя |
| MessagePack | 669 байт | есть `bin` | не задана спецификацией | схема внешняя |
| CBOR (canonical) | 669 байт | есть `bytes` | задана в RFC 8949 §4.2 | схема внешняя |

CBOR и MessagePack дают одинаковый размер на этих структурах (на 27 % меньше
JSON), но канонический режим CBOR гарантирует одинаковые байты для одинаковых
логических структур, а MessagePack — нет: порядок ключей и представление чисел
зависят от реализации. Для подписи записей DHT и для детерминированного
`NodeID` это решающее различие, поэтому выбран CBOR.

## Идентичность и NodeID

Открытый ключ узла — Ed25519. `canonical_encode(public_key)` — DER
`SubjectPublicKeyInfo` (44 байта для Ed25519), канонический по построению.

```text
NodeID = SHA-256(canonical_encode(identity_public_key))[:NODE_ID_BITS / 8]
```

`NODE_ID_BITS` по умолчанию 256 — это в точности формула раздела 9 ТЗ.
Меньшие значения (кратные 8) допустимы как исследовательский параметр
раздела 14: они увеличивают плотность заполнения k-bucket на малом числе узлов
и не меняют формат кадра.

Обязательные проверки при любом получении открытого ключа:

1. `NodeID` повторно вычисляется из ключа и сравнивается с заявленным;
2. при защищённом канале ключ из TLS-сертификата совпадает с ключом из
   `HELLO`.

Закрытый ключ хранится только в каталоге состояния узла
(`state_dir/identity/ed25519-private.pem`, права 0600) и никогда не передаётся
по сети и не коммитится.

## Рукопожатие HELLO

Каждое новое соединение начинается обменом:

```text
инициатор                         принимающая сторона
    | -------- HELLO -------------> |
    |                               | проверка NodeID = SHA-256(key),
    |                               | совпадения с TLS-ключом и с ожидаемым
    | <------- HELLO_OK ----------- |
    | <------- ERROR(0x08) -------- |  (при нарушении, далее разрыв)
```

Payload `HELLO` и `HELLO_OK`:

```text
{
  "version": 1,            # версия рукопожатия
  "node_id": bytes(32),    # усечённый до NODE_ID_BITS
  "key":     bytes(44),    # DER SubjectPublicKeyInfo
  "host":    str,          # объявленный адрес
  "port":    uint16
}
```

Если объявленный адрес пуст, недопустим или равен `0.0.0.0`/`::`,
принимающая сторона использует адрес сокета.

При отказе принимающая сторона отправляет `ERROR` с кодом `IDENTITY_MISMATCH`
и закрывает соединение, не выполняя прикладных действий. Узел, получивший
такой отказ, считает рукопожатие неуспешным.

Bootstrap-контакт (адрес известен, `NodeID` ещё нет) допускается только при
`allow_bootstrap_trust = true`. Во всех остальных случаях ожидаемый `NodeID`
известен из записи DHT и сверяется.

## Структуры сообщений

Ниже `bytes(N)` — CBOR `bytes` длины `N`, `uint` — беззнаковое целое.

### PING / PONG

```text
PING  {}
PONG  {"ok": bool, "node_id": bytes(32)}
```

### FIND_NODE

```text
FIND_NODE_REQUEST  {"target": bytes(32), "count": uint}
FIND_NODE_RESPONSE {"contacts": [Contact, ...], "node_id": bytes(32), "total": uint}
```

`count` ограничивается сервером значением `K_BUCKET_SIZE`; ответ содержит не
более `K_BUCKET_SIZE` валидных контактов в порядке возрастания XOR-расстояния
до `target`.

### Contact

```text
Contact {
    "id":   bytes(32),   # NodeID
    "key":  bytes(44),   # DER SubjectPublicKeyInfo
    "host": str,
    "port": uint16
}
```

Контакт принимается только после проверки `NodeID = SHA-256(key)` и формата
адреса. Некорректный контакт отбрасывается, остальные контакты ответа
обрабатываются.

### STORE

```text
STORE_REQUEST  {"key": bytes(32), "record": NodeRecord}
STORE_RESPONSE {"stored": bool, "reason": str, "sequence_number": uint}
```

Хранитель проверяет запись целиком и отвечает причиной отказа, а не кадром
ошибки: отказ по TTL, подписи или версии — штатный результат операции, а не
нарушение протокола. Хранитель обязан убедиться, что `key` совпадает с
`record.record_key`; запись под чужим ключом отклоняется.

### FIND_VALUE

```text
FIND_VALUE_REQUEST  {"key": bytes(32)}
FIND_VALUE_RESPONSE {"found": true,  "value": NodeRecord}
FIND_VALUE_RESPONSE {"found": false, "contacts": [Contact, ...], "node_id": bytes(32)}
```

Если значения нет, возвращаются ближайшие к ключу контакты, и инициатор
продолжает итеративный поиск. Найденное значение проверяется инициатором
независимо от хранителя: подпись, `NodeID`, TTL, соответствие ключу. Запись,
не прошедшая проверку, отбрасывается, поиск продолжается без этого узла.

### NodeRecord

```text
NodeRecord {
    "node_id":              bytes(32),
    "identity_public_key":  bytes(44),
    "addresses":            [{"host": str, "port": uint16}, ...],
    "sequence_number":      uint,
    "issued_at":            uint,   # unix time, секунды
    "expires_at":           uint,   # unix time, секунды
    "signature":            bytes(64)
}
```

Каноническое представление — канонический CBOR **без** поля `signature`.
Подпись Ed25519 вычисляется ровно по этим байтам и покрывает все остальные
поля, включая список адресов и оба времени.

Ключ хранения и поиска записи:

```text
record_key = SHA-256("node:" || NodeID)
```

Обязательные проверки записи (выполняются и хранителем, и инициатором):

| Проверка | Отказ |
|---|---|
| длина `node_id` равна разрядности сети | `MalformedRecord` |
| `NodeID = SHA-256(identity_public_key)` | `RecordIdentityMismatch` |
| подпись по каноническим байтам | `BadRecordSignature` |
| размер закодированной записи ≤ `max_record_bytes` | `RecordTooLarge` |
| число адресов 1..`max_addresses`, формат host/port | `BadAddress` |
| `issued_at ≤ now + 60`, `expires_at > now` | `NotYetValidRecord`, `ExpiredRecord` |
| `expires_at > issued_at`, TTL ≤ 4 × `record_ttl_seconds` | `NotYetValidRecord` |
| `key = record_key` | `RecordError` |
| `sequence_number` не меньше сохранённого | `StaleRecord` |

Из нескольких валидных записей владельца используется запись с наибольшим
`sequence_number`; запись с меньшим номером считается попыткой отката.
Запись с тем же номером и другим содержимым также отклоняется.

Пример (тест-вектор: закрытый ключ `00 01 .. 1f`, `issued_at = 1700000000`):

```text
node_id              a050837d85070582ccf7394b0988847cc312cb88259b894899f6f239cf1791a5
identity_public_key  302a300506032b657003210003a107bff3ce10be1d70dd18e74bc09967e4d6309ba50d5f1ddc8664125531b8
addresses            [{"host": "192.168.10.24", "port": 7000}]
sequence_number      3
issued_at            1700000000
expires_at           1700000180
signature            43101815896008b0f42a6efd7a48bfb9deb3548e272f05375440333673e91828
                     317c1a843a9a6b1c12c79dd8e6880053de16ad24e5615d81ac56817175f60409
record_key           7bf392b33124eb668fcd4927a436c87c6e54c25ec33ec906a3bc9470fb571b24
```

Размер канонических подписываемых байтов — 196, всей записи с подписью — 272.

### Репликация и жизненный цикл записи

* владелец публикует запись на `R = 3` ближайших к `record_key` доступных
  узлах, всегда сохраняя копию локально;
* операция успешна при не менее чем `store_success_acks = 2` подтверждениях;
* `TTL` выбирается в диапазоне 120–300 секунд (`record_ttl_seconds`);
* интервал переопубликования равен `record_ttl_seconds × republish_fraction`
  и не превышает половины TTL; каждое переопубликование увеличивает
  `sequence_number`;
* истёкшие записи удаляются из хранилища и не выдаются по `FIND_VALUE`;
* при поиске найденная валидная запись сохраняется и инициатором, что
  увеличивает число хранителей без ручного вмешательства.

## Туннель

Туннель — зафиксированная последовательность различных узлов от инициатора к
получателю. Инициатор и получатель не считаются промежуточными узлами.
Маршрут передаётся целиком в первом кадре `TUNNEL_BUILD`, поэтому каждый
ретранслятор видит только свой индекс и следующий переход.

### RouteHop

```text
RouteHop {
    "node_id": bytes(32),
    "key":     bytes(44),
    "host":    str,
    "port":    uint16
}
```

Адрес берётся из проверенного контакта таблицы маршрутизации; при подключении
к следующему переходу `NodeID` сверяется с TLS-сертификатом (см. раздел
«Защита канала»), поэтому инициатор не может направить трафик не тому узлу.

### TUNNEL_BUILD / TUNNEL_BUILD_OK / TUNNEL_BUILD_FAIL

```text
TUNNEL_BUILD      {"tunnel_id": bytes(16), "route": [RouteHop, ...],
                   "index": uint, "ttl": uint, "max_hops": uint}
TUNNEL_BUILD_OK   {"tunnel_id": bytes(16), "index": uint, "node_id": bytes(32)}
TUNNEL_BUILD_FAIL {"tunnel_id": bytes(16), "code": uint, "detail": str}
```

Построение выполняется рекурсивно: ретранслятор `i` проверяет, что
`route[index].node_id` совпадает с его собственным `NodeID`, валидирует маршрут
(отсутствие петель и дубликатов, лимит `max_hops`, не менее `min_relays`
ретрансляторов, положительный `ttl`), затем отправляет `TUNNEL_BUILD` с
`index + 1` следующему переходу и возвращает полученный ответ предыдущему.
Поэтому `TUNNEL_BUILD_OK` означает, что включение подтвердили **все** узлы
цепочки, а не только первый ретранслятор.

При отказе любого перехода возвращается `TUNNEL_BUILD_FAIL` с причиной; узлы,
уже создавшие состояние, его удаляют. Инициатор повторяет попытку с другим
набором ретрансляторов, исключая отказавших.

### TUNNEL_DATA / TUNNEL_ACK / TUNNEL_CLOSE

```text
TUNNEL_DATA  {"tunnel_id": bytes(16), "seq": uint, "payload": bytes}
TUNNEL_ACK   {"tunnel_id": bytes(16), "seq": uint}
TUNNEL_CLOSE {"tunnel_id": bytes(16)}
```

`TUNNEL_DATA` передаётся в обе стороны. Ретранслятор запоминает, с какого
соединения пришёл кадр, и пересылает его на противоположную сторону цепочки;
содержимое `payload` не модифицируется и не интерпретируется. Получатель
подтверждает каждый кадр `TUNNEL_ACK`, который возвращается к инициатору тем же
путём. Подтверждение используется для контроля доступности и для проверки
доставки.

`TUNNEL_CLOSE` освобождает состояние всех ретрансляторов цепочки.

### End-to-end канал

Внутри `TUNNEL_DATA.payload` передаются записи отдельной TLS 1.3-сессии между
инициатором и получателем. Сессия реализована через `ssl.MemoryBIO` и не
привязана к сокету, поэтому её кадры переносятся как обычная полезная нагрузка
туннеля.

* обе стороны предъявляют сертификаты стенда и проверяют цепочку;
* ключ сертификата удалённой стороны сверяется с ожидаемым `NodeID`
  получателя, поэтому ретранслятор не может выдать себя за него;
* поверх TLS-сессии прикладные сообщения кадрируются 4-байтовой длиной и
  кодируются каноническим CBOR;
* ретранслятор видит только `tunnel_id`, номер кадра и ciphertext.

### Прикладные сообщения

```text
APP_MESSAGE  {"kind": "app_message", "message_id": bytes(16), "from": bytes(32),
              "text": str, "sent_at": float}
APP_ACK      {"kind": "app_ack", "message_id": bytes(16), "status": str,
              "received_at": float}
```

`status` принимает значения `delivered`, `duplicate` или `rejected`.
`message_id` уникален для сообщения и переживает переподключение: повтор с тем
же `message_id` от того же отправителя не создаёт второго прикладного действия
и подтверждается статусом `duplicate`. Поле `from` сверяется с `NodeID`,
подтверждённым сертификатом e2e-сессии; при несовпадении сообщение
отклоняется.

## Защита канала

Межузловые TCP-соединения защищаются TLS 1.3 с взаимной аутентификацией
(раздел 11.2 ТЗ).

**Версии.** `minimum_version = maximum_version = TLSv1_3`. TLS 1.2 и более
ранние версии отклоняются на этапе рукопожатия, откат версии невозможен.

**0-RTT.** Не используется: `max_early_data` не задаётся, asyncio не открывает
ранние данные, сервер не принимает early data. Повтор ранних данных исключён.

**Сертификаты.** Стенд имеет собственный корневой сертификат (CA). Каждый узел
предъявляет сертификат, подписанный этим CA, и проверяет цепочку удалённой
стороны до CA (`verify_mode = CERT_REQUIRED`). `check_hostname = False`
используется только потому, что идентичность узла задаётся `NodeID`, а не
DNS-именем; проверка цепочки при этом не отключается.

Ключ сертификата узла — его долговременный identity-ключ Ed25519, поэтому
`NodeID` вычисляется из того же открытого ключа, что и в сертификате.

**Привязка к NodeID.** Поверх проверки цепочки приложение обязано:

1. извлечь `SubjectPublicKeyInfo` из сертификата удалённой стороны;
2. повторно вычислить `NodeID = SHA-256(SPKI)[:NODE_ID_BITS/8]`;
3. сравнить результат с `NodeID`, заявленным в `HELLO`;
4. сравнить с ожидаемым `NodeID`, если он известен из записи DHT.

Валидный сертификат любого участника стенда сам по себе не позволяет выдать
себя за другой узел: без закрытого ключа владельца нельзя пройти
`CertificateVerify` для чужого `NodeID`.

**Режим `plain`.** Существует только для изолированных тестов транспорта и DHT,
явно помечается в журнале и метриках, не используется в приёмочных сценариях.

### Учёт повторов

* `request_id` каждого запроса уникален (16 случайных байт); узел помнит
  принятые идентификаторы в пределах соединения и на повтор отвечает
  `ERROR` с кодом `REPLAY_DETECTED`, не выполняя прикладного действия;
* `session_id` — 16 случайных байт на соединение; используется как область
  действия учёта и в журналах;
* `message_id` прикладного сообщения (раздел «Прикладные сообщения») —
  постоянный идентификатор, который переживает переподключение и учитывается
  отдельным ограниченным кэшем;
* повтор кадра из завершённой сессии отклоняется на уровне TLS: ключи сессии
  разные, запись не расшифровывается, соединение закрывается.

Проверки реализованы в `transport/tcp.py` (идентификаторы кадров) и
`security/replay.py` (прикладные сообщения).

## Обработка ошибок

Обязательные случаи и реакция:

| Случай | Реакция |
|---|---|
| частичный заголовок | ожидание, буфер не более 24 байт |
| частичный payload | ожидание, буфер не более `24 + payload_length` |
| несколько кадров в одном чтении | все кадры обрабатываются по порядку |
| неизвестный тип | `BadType`, соединение закрывается, узел работает |
| неверная версия | `BadVersion`, соединение закрывается, узел работает |
| превышение длины | `PayloadTooLarge` до выделения буфера |
| тайм-аут запроса | `TimeoutExpired`, узел помечается неудачным |
| разрыв внутри кадра | соединение закрывается, текущий кадр отбрасывается |
| ответ с чужим `request_id` | игнорируется, ожидание продолжается |
| ошибка в обработчике кадра | `ERROR` с кодом `INTERNAL`, узел продолжает работу |
